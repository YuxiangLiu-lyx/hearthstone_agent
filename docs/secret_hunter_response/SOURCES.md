## PredatorMCTS

Source: <https://hearthstoneai.github.io/files/bots/PremadeDeckPlaying2018/BotPredatorMCTS.zip>, the [competition archive](https://hearthstoneai.github.io/botdownloads.html) names Max Frick and Ünal Akkaya, first in 2018 premade decks. The archive has source timestamps through May 30, 2019; no commit identifier or explicit license is included. We read source only, execute no external binary, copy no external code, and independently implement the ideas.

Read `MCTS/MCTSSimulatorExt.cs`: `simulate`, `getPredictionMap`, `simulateOpponentWithPrediction`, `updateTasks`, `predictDeckClasses`; also `Reader/BigramMap.cs`, `Reader/BigramMapReader.cs`, and `readme.txt`. `getPredictionMap` collects public play history, predicts cards/decks, removes seen cards from proposed decks and uses the observable hand count. `simulate` shortlists valuable leaves. `simulateOpponentWithPrediction` divides each leaf's budget among proposed hands, advances an opponent response, then searches the player's continuation. We adapt the selective endpoint -> public-compatible response -> known-hand recovery structure. We do not reconstruct actual hidden hands, reproduce its MCTS scoring, or import its top-tier deck lists. Our runtime hypotheses are bounded sensitivity scenarios, not calibrated probabilities of hand possession.

`Bigramms/bigramm_3-2018-10-2017.json.gz` has `cardIds` and `bigramMap`: the latter is a list of card-ID maps to records `{cardId, numOcc}`. These are old card co-occurrences, not next-turn labels. Of 1,814 IDs, 352 intersect the 367-card course catalog. Class+neutral intersections are 165 Warlock, 168 Hunter, 166 Mage. Each feature calculation additionally filters affordable course cards of the observed opposing class. The older 2016–2017 archive has 1,198 IDs and 1,191 map entries; only the 2017–2018 archive is used in the preregistered ablation. Data stays offline. `calibration.json` records its negative predictive result.

## Cardsformer

Pinned source: <https://github.com/WannianXia/Cardsformer/tree/6a0cba16298c5262ee204eeda97409064cc683b2>. Read `README.md`, `gen_data.py`, `PredictionDataset.py`, `eval.py`, `Env/Hearthstone.py`, `Env/EnvWrapper.py`, `Model/PredictionModel.py`, and the card CSV. No LICENSE file is present in the pinned tree. No code or model is redistributed.

`gen_data.py` collects action-conditioned current features and actual next-state minion/hero tensors from the simulator; `PredictionDataset.__getitem__` exposes these separate transition targets. `eval.py` first predicts state features, then gives them to the policy model for action-value selection. We retain this separation: official-engine transitions are verified independently of terminal continuation outcomes. A legal/correct transition is not evidence of a better plan.

Checkpoint comparison was rejected on concrete compatibility grounds before a large download: evaluation requires CUDA, PyTorch, transformers/MPNet, pythonnet 2.5.2 and Mono, plus SabberStone DLLs. None of torch/clr/transformers is installed in the course Python environment. Its state tensors have 23 hand, 26 minion and 31 hero features with 768-dimensional language embeddings, while this course provides JSON actions/observations through Fireplace. `modify_cards` changes historical stats (e.g. Knife Juggler attack 3), while course Juggler attack is 2. The checkpoint would therefore require environment, feature, action-space and card-semantics adaptation; this is not a low-cost compatible comparison. No claim of reproduced checkpoint performance is made.

## Action-count search allocation

Source: <https://hearthstoneai.github.io/files/bots/PremadeDeckPlaying2020/SebastianMiller.zip>. Competition archive lists Sebastian Miller first in the 2020 premade track. The first assigns depths 3/2/1 when valid action counts are below 5, between 5 and 24, or at least 25, with a legal end-turn fallback. Two source files, dated July 8, 2020; no explicit license or commit ID. We independently adapt branching-aware depth selection, retain state deduplication, and cap total nodes/deadline. This fits the endpoint/recovery branching cost better than migrating an entire external graph-search engine.
